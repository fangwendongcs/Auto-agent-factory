# V0.16 Real DeepSeek Read-only Contract Verified

V0.16 verifies that the local n8n workflow can complete a real DeepSeek V4 Pro call through the OpenAI-compatible read-only provider path while preserving the review-first safety boundary.

This record is based on a local runtime verification. It does not include credentials, provider secrets, raw private payloads, or any workflow runtime modification.

## Verification Summary

- Local n8n runtime was healthy.
- Agent Task Executor entered the `real-readonly` provider path.
- OpenAI-compatible HTTP Request completed a real DeepSeek V4 Pro call.
- `provider_call_status = response_received`.
- `provider_response_raw.model = deepseek-v4-pro`.
- Provider response completed with `finish_reason = stop`.
- `message.content` returned complete JSON.
- Provider Response Normalizer parsed `summary`, `evidence`, and `risk_summary`.
- Result Normalizer generated `agent_result`.
- `agent_result.status = needs_review`.
- `agent_result.provider.mode = real-readonly`.
- `agent_result.provider.name = openai-compatible-readonly`.
- `agent_result.provider.model = deepseek-v4-pro`.
- Evidence entries `c1` and `c2` both returned `pass`.
- Read-only and human review safety boundaries remained in place.
- No API key exposure was observed.

## Current Capability

The project can now demonstrate a real read-only provider contract:

1. A local master workflow can trigger the Agent Task Executor.
2. The executor can route into the real read-only provider path.
3. The provider request can call DeepSeek V4 Pro through the OpenAI-compatible adapter.
4. The provider response can be normalized into the existing `agent_result` contract.
5. The final result remains review-oriented with `needs_review`, not autonomous execution.

This is a contract verification milestone, not a production autonomy milestone.

## Safety Boundary

The verified path remains constrained:

- No workflow shell execution.
- No workflow file writes.
- No workflow Git modification.
- No deployment action.
- No external write action.
- No automatic approval.
- Human review remains required for follow-up action.
- Provider credentials stay in n8n Credentials and are not stored in the repository.

## Known Limits

- The verified provider path is read-only and review-only.
- Real provider calls still depend on local n8n runtime health and credential setup.
- Provider output quality still depends on model behavior and prompt constraints.
- Long or complex tasks may need higher `provider_max_tokens` or task splitting.
- Failure recovery is not yet a full policy engine; V0.17 should classify retry, stop, and needs-review outcomes.

## V0.17 Next Step

V0.17 Recovery Policy should turn provider and workflow failures into bounded recovery decisions:

- `retry` for transient provider timeouts, aborts, and truncated outputs.
- `needs_review` for ambiguous provider results, safety boundary uncertainty, or malformed evidence.
- `stop` for forbidden actions, repeated failures, or unrecoverable validation errors.

The policy should preserve the same read-only and human-review boundaries verified in V0.16.
