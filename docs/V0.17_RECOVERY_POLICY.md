# V0.17 Recovery Policy

V0.17 defines a bounded local recovery policy for failed, timed-out, truncated, or review-gated runs. It is a repo-side contract and utility layer first; it does not modify n8n runtime behavior or enable write actions.

## Goal

Turn failures into one of three reviewable decisions:

- `retry`: try the read-only provider path again within a bounded retry budget.
- `needs_review`: stop automatic retry and ask a human to inspect the run.
- `stop`: do not retry; preserve the failure record and safety boundary.

## Contract

The recovery policy payload is validated by `src/schema/recovery-policy.schema.json`.

Required fields include:

- `policy_version`
- `run_id`
- `task_id`
- `error_class`
- `decision`
- `next_action`
- `max_retries`
- `retry_count`
- `timeout_minutes`
- `stop_conditions`
- `reason`
- `safety`

The safety block always keeps:

- `read_only = true`
- `write_actions_enabled = false`
- `requires_human_review = true`
- `secrets_included = false`

## Classification Rules

| Error class | Decision before retry limit | Decision at retry limit | Next action |
|---|---|---|---|
| `provider_timeout` | `retry` | `stop` | `retry_provider_readonly` or `stop_run` |
| `provider_aborted` | `retry` | `stop` | `retry_provider_readonly` or `stop_run` |
| `provider_output_truncated` | `retry` | `stop` | `retry_provider_readonly` or `stop_run` |
| `timeout` | `retry` | `stop` | `retry_provider_readonly` or `stop_run` |
| `provider_invalid_json` | `needs_review` | `needs_review` | `manual_review` |
| `provider_response_missing` | `needs_review` | `needs_review` | `manual_review` |
| `malformed_evidence` | `needs_review` | `needs_review` | `manual_review` |
| `empty_response` | `needs_review` | `needs_review` | `manual_review` |
| `approval_blocked` | `needs_review` | `needs_review` | `manual_review` |
| `provider_error` | `needs_review` | `needs_review` | `manual_review` |
| `input_error` | `stop` | `stop` | `stop_run` |
| `workflow_config_error` | `stop` | `stop` | `stop_run` |
| `forbidden_action` | `stop` | `stop` | `stop_run` |
| `unknown` | `needs_review` | `needs_review` | `manual_review` |

## Retry Limits

Defaults:

- `max_retries = 2`
- `retry_count = 0`
- `timeout_minutes = 15`

Bounds:

- `max_retries` is clamped from 0 to 3.
- `retry_count` is clamped from 0 to 3.
- `timeout_minutes` is clamped from 1 to 30.

A transient provider failure can retry only while `retry_count < max_retries`. Once the retry budget is exhausted, the policy returns `stop`.

## Stop Conditions

Stop conditions are explicit strings attached to the policy. Current stop conditions include:

- `retry_budget_exhausted`
- `<error_class>_is_not_recoverable_by_retry`
- `human_review_required_before_retry`
- `unclassified_error_requires_review`

These strings are meant for local audit, future workflow routing, and human-readable run review.

## Needs-review Output

`needs_review` means no automatic retry and no write action. The reviewer should inspect:

- the sanitized run identifier
- the error class and reason
- provider mode and model if available in the surrounding run summary
- whether the failure is a prompt/output issue, runtime issue, or safety issue
- whether a retry should be manually requested with adjusted criteria or provider settings

## Current Implementation

- `src/utils/generateRecoveryPolicy.js` creates recovery policy payloads.
- `scripts/generate-recovery-policy.mjs` exposes the policy as a local CLI.
- `examples/recovery/sample_provider_timeout.json` provides a safe retry example.
- `tests/recovery-policy.test.js` verifies retry, stop, needs-review, retry limit, and secret refusal behavior.
- `tests/recovery-policy-cli.test.js` verifies the CLI output and secret refusal path.
- `src/schema/recovery-policy.schema.json` validates the contract.

Run the local CLI:

```bash
npm run recovery:policy
```

The CLI prints recovery policy JSON to stdout. It does not connect to n8n, does not retry automatically, and does not write files.

## Safety Boundary

V0.17 does not enable:

- shell execution
- file writes from workflow
- Git modification
- deployment
- external write actions
- automatic human approval
- storing provider credentials in docs, examples, workflow JSON, or frontend code
