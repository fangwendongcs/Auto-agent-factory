# V1.0 Local Production Workflow Readiness Runbook

This runbook connects the verified V0.15-V0.19 pieces into one end-to-end local production workflow readiness path. It proves that local tasks can be validated, run through a read-only provider path, recovered, reviewed, and handed off as drafts before any Codex, Git, file, shell, deployment, or external write action is allowed.

V1.0 readiness means local production workflow readiness, not autonomous production execution.

## Safety Line

Always keep these boundaries:

- no API keys, tokens, passwords, or credential plaintext in docs, examples, workflow JSON, tests, screenshots, prompts, or Git
- no automatic retry
- no automatic approval
- no workflow file-write action
- no shell execution from workflow
- no Git modification from workflow
- no deployment action
- no external write action
- no public unauthenticated production webhook exposure

Secrets must stay in n8n Credentials or local ignored env files only.

## Readiness Flow

```text
V0.15 local runtime health
-> V0.16 DeepSeek read-only provider contract
-> V0.17 recovery policy
-> V0.18 human approval console
-> V0.19 action draft handoff
-> V1.0 readiness decision
```

## Step 3: DeepSeek Read-only Provider Contract

Prepare the sandbox payload without sending it:

```bash
npm run sandbox:deepseek:readonly
```

Expected default behavior:

- dry-run payload generation succeeds
- no remote webhook post is made by default
- no provider key is required in the repo

For a real local n8n run, enable sending only from your local shell after confirming the n8n credential is configured:

```bash
DEEPSEEK_SANDBOX_SEND_ENABLED=true npm run sandbox:deepseek:readonly
```

Expected real-readonly acceptance:

- Master triggers successfully
- Executor enters the real read-only provider path
- Provider call returns structured content
- `agent_result.status = needs_review`
- provider mode/name/model are present
- read-only and human-review boundaries remain intact

Do not store raw provider payloads or credential material in the repo.

## Step 4: Recovery Policy

Generate a local recovery policy:

```bash
npm run recovery:policy
```

Expected:

- `policy_version = v0.17-local-recovery-policy`
- decision is one of `retry`, `stop`, or `needs_review`
- `next_action` is advisory only
- `safety.requires_human_review = true`
- `safety.write_actions_enabled = false`

For the verified controlled failure path:

- Error Handler runtime triggers
- Recovery Advisor emits `recovery_policy`
- `provider_5xx` maps to `error_class = provider_5xx`
- `decision = retry`
- `next_action = retry_provider_readonly`
- no automatic retry is enabled

## Step 6: Action Draft Handoff

Run the default action draft:

```bash
npm run action:draft
```

Verify the three handoff states:

```bash
node scripts/generate-action-draft.mjs examples/action-drafts/sample_v018_rejected_decision_record.json
node scripts/generate-action-draft.mjs examples/signoff-decisions/sample_needs_review_decision_record.json
node scripts/generate-action-draft.mjs examples/signoff-decisions/sample_readonly_approved_decision_record.json
```

Expected mapping:

| Human decision | Handoff status | Expected behavior |
|---|---|---|
| `rejected` | `blocked_rejected` | Do not implement; convert rejection reason into review notes only. |
| `needs_review` | `blocked_needs_review` | Do not implement; prepare questions and review checklist. |
| `approved` | `draft_after_approval` | Generate draft-only handoff; do not execute automatically. |

All drafts must keep:

- `Draft only: yes`
- `Write actions enabled: no`
- no secrets or raw provider payloads
- no instruction that bypasses human approval
